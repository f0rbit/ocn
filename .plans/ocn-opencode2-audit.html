Plan: OCN OpenCode2 compatibility audit

todo

Restore and harden OCN for OpenCode 2 beta while preserving the existing tmux status-right and SketchyBar agents surfaces. The audit already proves that OpenCode2 is healthy and the local status scripts execute, but no OCN plugin is active, the package is typed against the V1 plugin API, and the active configuration does not register it. User decisions are locked: V2-only (V1 dropped), local-path registration bootstrappable from the dotfiles setup, TTL expiry with automatic resurrection, one package PR at feature end.

Root cause

Stated goal: Investigate why OCN, tmux, and SketchyBar appear broken after switching to opencode2, then audit and repair the integration.

Underlying need: Establish one verified, version-aware event-to-state contract between the OpenCode2 service and the existing status consumers, with installation and diagnostics that fail visibly instead of silently rendering zero sessions.

Why this matters: The current live probes show opencode2 v0.0.0-beta-18684 is healthy, both OCN symlinks execute, and the OCN test suite passes, yet /api/plugin reports only built-ins and the state directory is empty. The widget is therefore downstream of a missing/incompatible producer, not primarily a tmux or SketchyBar rendering defect. OpenCode2 intentionally breaks V1 plugins and uses a shared service whose process identity cannot represent a session.

Alternatives considered

Option 1: Native OpenCode2 plugin with session-keyed file state

recommended

Port OCN to the V2 define({ id, setup }) plugin API, subscribe to the service event stream from the plugin context, normalize only the events needed by OCN, and keep the existing file boundary for tmux and SketchyBar. Replace PID-only identity with canonical location plus session identity and retain an in-memory repository for tests.

Real-world examples

  • OpenCode V2 Promise plugins — use a typed define/setup entrypoint and imperative registrations rather than the V1 returned-hooks object. source
  • OpenCode TUI event context — consumes the server event stream and filters events by project/location, the same service-owned event boundary OCN needs. source

Pros

  • Uses the supported OpenCode2 extension point, so no extra daemon or polling race is needed.
  • Preserves the current tmux and SketchyBar contracts and their quiet, integration-first presentation.
  • Session-keyed state fixes both shared-service PID collisions and multiple sessions in one location.

Cons

  • The V2 plugin API is beta and the published docs currently need to be checked against the exact package bundled by beta-18684 before implementation.
  • Dropping V1 support is a public package compatibility break unless the user explicitly wants a dual-runtime release.

Option 2: Standalone OpenCode2 client watcher

Do not load a plugin. Run one OCN-owned watcher that connects to the shared service through the V2 client or /api/event, maintains session state, and writes the same files consumed by tmux and SketchyBar.

Real-world examples

  • OpenCode API clients — the documented V2 client and api command use the generated HTTP contract and expose /api/event, /api/session/active, and /api/health. source
  • tmux format commands — tmux deliberately supports external #() commands in status formats, which is the existing OCN consumer pattern. source

Pros

  • Decouples OCN from the unstable plugin implementation API and observes the shared service as a normal client.
  • One watcher can naturally aggregate multiple locations and sessions.

Cons

  • Introduces a process lifecycle, restart, duplicate-watcher, and launch-at-login problem that OCN intentionally avoided.
  • Permissions/authentication and service discovery become production concerns; tmux and SketchyBar can show stale data while the watcher is down.

Option 3: One package with V1 and V2 runtime adapters

Keep the current V1 returned-hooks entrypoint and add a V2 entrypoint selected by package export/configuration, sharing the domain adapter, state repository, and consumers underneath.

Real-world examples

  • Node.js conditional exports — packages expose multiple supported entrypoints while keeping a single package boundary and explicit conditions. source

  • Preserves existing V1 users while giving this machine a V2 path.
  • Shared state and rendering fixes still address the real consumer problems.

Cons

  • Two plugin entrypoints, two SDK contracts, and two fixture suites increase release and debugging cost for a small personal package.
  • Configuration can accidentally load the wrong entrypoint; duplicated lifecycle semantics undermine the single-source goal.

Option 4: Pin V1 and defer the OpenCode2 port

Keep OCN unchanged, run the old opencode binary for notification sessions, and treat OpenCode2 as unsupported until its plugin API stabilizes.

Real-world examples

Pros

  • Lowest immediate code risk and no dependency on an unfinished V2 plugin contract.

  • Does not solve the user's current OpenCode2 workflow; the active service already has no OCN state.
  • Maintains stale PID-based state and silently broken installation guidance, increasing future migration cost.

Architecture decisions

  • Target V2 only — decided. The active binary is beta-18684 and official migration docs say V1 plugins do not work in V2. The user has confirmed dropping V1 support: the package uses the exact V2 plugin API (define({ id, setup })) and the V1 entrypoint is deleted. This is the principal breaking change below.
  • Preserve the file boundary. The tmux status command and SketchyBar agent widget already consume the right kind of stable, inspectable boundary. The producer changes; the existing surfaces do not become a new page, daemon, or widget.
  • Use session identity, not process identity. V2's shared service means a PID identifies the service, not a project/session. State records must carry a stable key derived from canonical location and session ID, plus owner/service metadata for cleanup. Idle records expire via a configurable TTL (decided): readers skip and cleanup removes records whose updated_at exceeds the TTL; any subsequent event for the same session rewrites the record, so expiry is non-destructive and sessions resurrect automatically. Explicit session-deletion events remove records immediately; PID liveness is only a fallback for dead service owners.
  • Make external boundaries typed twice. Import the exact SDK/V2 types so compilation catches package drift, then validate event and persisted JSON at runtime with Zod. Unknown event types and malformed state files are ignored with diagnostics, never coerced into valid-looking zero sessions.
  • Use Provider-style seams. An event source and a state repository each get a production implementation and an in-memory implementation. Tests exercise the plugin workflow without HTTP, service, filesystem, tmux, or OS-notification mocks.
  • Minimize API surface if the fallback is needed. The standalone path may use only service discovery/health, /api/event, and optionally /api/session/active for reconciliation. It must not invent an unauthenticated direct URL when the OpenCode client can discover the service.
  • Integration-first UI decision. No new page, nav item, or top-level surface is proposed. The existing tmux status-right and SketchyBar agents widget already own the user's “what agent sessions need attention?” job; this work only repairs their producer and preserves their compact Tokyo Quiet hierarchy. The page-vs-integrate gate is therefore not applicable, and adding a separate OCN dashboard would be aggregation rather than a distinct job.
